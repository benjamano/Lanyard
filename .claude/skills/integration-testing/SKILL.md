# Integration testing with `CustomWebApplicationFactory`

`src/Lanyard.Tests/Integration/CustomWebApplicationFactory.cs` is a `WebApplicationFactory<Program>` that boots the real app — real auth middleware, real routing, real `RouteAuthorizationGate`, real controllers — against an isolated EF InMemory database. Reuse it rather than building a new factory from scratch; it already solves several non-obvious problems specific to this app.

## What it took to get working (know these before touching it)

**The `Program` marker.** `Lanyard.App`'s `Program.cs` uses top-level statements, which generate an `internal` `Program` class invisible outside that assembly. `Program.cs` ends with `public partial class Program;` specifically so `WebApplicationFactory<Program>` in the test project can see it. If this marker is ever removed (e.g. during an unrelated Program.cs refactor), every integration test fails to compile — grep for `public partial class Program` before assuming it's safe to delete.

**The EF dual-provider conflict.** Program.cs hardcodes `AddDbContextFactory<ApplicationDbContext>(options => options.UseNpgsql(...))` with no seam to swap providers. Naively removing `DbContextOptions<ApplicationDbContext>`/`IDbContextFactory<ApplicationDbContext>`/`ApplicationDbContext` registrations and re-adding with `UseInMemoryDatabase(...)` throws at runtime: *"Services for database providers 'Npgsql...', 'Microsoft.EntityFrameworkCore.InMemory' have been registered... Only a single database provider can be registered."* This happens because `UseNpgsql` already registered Npgsql's *internal* EF services into the app's shared `IServiceCollection`, and removing the DbContext-specific registrations doesn't remove those. The fix `CustomWebApplicationFactory` uses: build a **separate, isolated** `IServiceProvider` just for the InMemory provider (`new ServiceCollection().AddEntityFrameworkInMemoryDatabase().BuildServiceProvider()`) and pass it via `options.UseInternalServiceProvider(...)` — this sidesteps the shared-container collision entirely instead of trying to surgically un-register Npgsql's services.

**`Development` environment is required, not just convenient.** `Program.cs` only skips `Database.MigrateAsync()` (which would throw against InMemory — relational migrations aren't a concept that provider supports) and only skips HTTPS-redirection/HSTS/forwarded-headers middleware (which would break a plain-HTTP test client) when `IsDevelopment()`. The factory calls `builder.UseEnvironment("Development")` for exactly these two reasons — don't remove it to "test production behavior" without re-solving both problems.

**The connection-string guard clause needs a non-empty dummy value.** `Program.cs` throws `InvalidOperationException` at startup if `ConnectionStrings:DefaultConnection` is empty — this check runs regardless of which provider ends up actually being used. The factory sets a syntactically-valid-looking but never-actually-connected-to placeholder via `builder.UseSetting(...)` purely to satisfy this guard before the real (InMemory) registration takes over.

**Logging in as the seeded admin.** `DatabaseSeeder.SeedAsync` (called unconditionally at the end of `Program.cs`, guarded internally against non-Postgres providers for its `ResetIdentitySequencesAsync` raw-SQL step) always seeds an admin user (`username: "admin"`) with roles Admin/Manager/Staff/CanControlMusic/CanClockIn. Its password is either read from `Seed:AdminPassword` config or, if unset, randomly generated per run (unusable in a test). `CustomWebApplicationFactory` sets `Seed:AdminPassword` to the known constant `CustomWebApplicationFactory.SeedAdminPassword` specifically so tests can `POST /api/auth/login` as this seeded admin and get a real authenticated session (cookie persists automatically on the `HttpClient` returned by `CreateClient()`, since `WebApplicationFactoryClientOptions.HandleCookies` defaults to `true`). Admins can log in via `POST /api/auth/login` with no `LocationId` — only non-admins need one.

**Hermeticity: OpenTelemetry reads its endpoint from a raw environment variable.** `UseOtlpExporter()` resolves `OTEL_EXPORTER_OTLP_ENDPOINT` via `Environment.GetEnvironmentVariable` directly (an OpenTelemetry SDK convention, not routed through `IConfiguration`), so a real developer machine with that variable set (pointing at the home Seq server) would make real outbound network calls during every test run otherwise. The factory's constructor overrides it to an inert `http://127.0.0.1:1` before the host builds, so tests don't depend on — or leak requests to — whatever's configured on the machine running them.

## Gotchas when writing new tests against it

- One `CustomWebApplicationFactory` instance = one isolated in-memory database (a fresh `Guid` name per instance). Create a new instance per test (`[TestInitialize]`/`[TestCleanup]`) for isolation — don't share one across tests unless you specifically want shared state.
- `WebApplicationFactoryClientOptions`'s redirect-following property is `AllowAutoRedirect` (singular) — not `AllowAutoRedirects`. Set it `false` when asserting on a redirect response directly rather than following it.
- A redirect's `response.Headers.Location` comes back as an **absolute** URI (e.g. `http://localhost/HandleLogin?...`), not the relative path you might expect from reading the `NavigateTo(...)` call in the source. Assert against `.AbsolutePath`, not `.OriginalString`, if you only care about the path.
- Background `IHostedService`s (`AutomationEngineHostedService`, `SongAnalysisHostedService`, `CourseRecurrenceHostedService`) really do start when the test host boots, same as in production. A benign `OperationCanceledException` from one of them logged at shutdown is expected (the channel reader gets cancelled when the test host disposes) — not a sign something's wrong.
